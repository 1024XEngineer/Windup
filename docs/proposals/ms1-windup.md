# 项目 1 · MS1 产品策划案

---

## 一、Windup 是什么

Windup 是一款专为想做游戏但没有美术资源的个人开发者与小型研发团队设计的 2D 游戏角色动态素材生成工具，覆盖从角色构思、动作生成到引擎导入的完整开发链路。用户只需提供文字描述或参考图，即可为特定角色定制全套动作序列，工具的最终交付物是一个包含成套动作与对应配置的完整资源包，免去开发者手工去背、切帧与调整对齐的重复性劳动。

与现有工具的差别在整条"从生成到入项目"的链路，而不止交付形态：它们交付的是一段动画的图片，Windup 交付的是一个跨动作始终一致、且能直接进游戏项目的角色。

在节奏上，Windup 采用"AI 生成、人确认"：AI 负责底层生成与自动质检，用户在角色卡确认、动作清单定制、逐帧检查三个节点掌握最终决定权。

与现有竞品相比，Windup 有四个关键差异：

- **交付即用，不止出图**：竞品交付止步 PNG + JSON，开发者仍要手工去背、切帧、对齐脚底线、命名、导引擎；Windup 自动完成这些工程后处理，交付放进项目就能用的素材包。
- **国产生态适配**：全面聚焦国产小游戏主线，导出资产专门针对 Cocos Creator 及国内微信、抖音等小游戏平台的技术规范进行深度结构适配。序列帧图集默认采用远程加载目录标准，依托七牛云存储与 CDN（可加可不加），资源导入引擎即可直接播放。
- **角色卡一致性**：同一角色在不同动作与批次间不会发生外观漂移。生成环节强制引入角色卡作为参照基准，使视觉一致性依靠工程系统保障，而非依赖模型的概率抽卡。
- **开源、中文**：项目开源、中文原生，可自部署、二次开发；生成模型与路线可替换，不被单一模型或厂商绑定。

Windup 现阶段的底层逻辑是“角色卡约束生成结合确定性工程后处理”。基于该架构，产品后续可以自然延伸至多视角渲染、非角色素材生成以及长期的游戏资产复用管理，也可快速接入如 Godot、Unity 等多引擎适配。

## 二、背景与战略决策

### 2.1 背景与机会

当前 AI 生图已能稳定产出精美的角色原画，但从单张图片到游戏可直接调用的动态资产之间，存在巨大的工程管线空白。行业当前普遍受制于四类问题：

- **跨动作一致性差**：同一角色扩展为多帧动作时，外观在帧间漂移——配饰位移、配色偏移、比例变化，得到的往往是"四个相似但并非同一个"的角色。
- **帧间稳定性不足**：相邻帧细节持续抖动，在游戏播放速度下呈现明显闪烁。
- **交付止步于图片**：现有工具产出的是"一张素材的图片，而非游戏素材"；开发者仍需手工完成去背、切帧、脚底线对齐、命名与引擎导入，该环节返工成本可达生成环节的十倍以上。

 骨骼动画路线在当前技术条件下也不成熟：公开失败实录显示，视觉模型难以准确理解图像坐标，导致部件拆分与锚点设置失准、骨骼层级关系混乱，同时，骨骼动画资源风格局限度很大，此为本项目不采用骨骼路线的依据之一。
 
海外垂类竞品（Ludo.ai、Meowa、PixelLab、Spriteflow 等）已能生成可用的单段动画，其中 Ludo、Meowa 最成熟，是本项目对标底线；但它们的交付同样止步于零散图像片段，上述问题仍是共同短板。

 真正的差异化空隙在国内小游戏生态：国内 2D 小游戏主要发行于微信、抖音平台。以微信小游戏为例，其畅玩榜前 100 中 Cocos 占比约 61%，开发管线高度依赖 Cocos 引擎，并受微信主包 4MB 体积限制，角色和美术一般走分包或远程 CDN。开发者规模约 40 万，其中八成为 30 人以下团队，目前市面上所有的 AI 生成工具无一针对该生态进行原生适配，这正是本项目的切入点。


### 2.2 目标用户与核心问题


主用户是国内小游戏赛道的个人开发者与微型团队中的程序、策划及非专业美术成员，他们会用引擎、写得动游戏逻辑，但缺乏美术产能；常见于横版动作、平台跳跃、Game Jam、独立游戏原型和微信小游戏开发。首期优先服务已有角色设定或参考图、需要快速补齐基础动作、使用 Cocos Creator / 微信小游戏或 Web 预览链路的用户。

需要解决的核心问题是：无法将 AI 生成的视觉设定，低成本地转化为符合国内小游戏工程规范、能够直接投入远程加载架构中运行的连贯动作资产。

### 2.3 战略决策与边界

**一句话决策**：放弃泛用型的动画生成路线，将国产小游戏（微信/Cocos）确立为未来两个月的首要主线，全力打通从输入到成套动作的明确生成工作流。

**本期范围**：

- **核心工作流**：跑通从"输入角色描述 / 参考图"到"得到单角色成套序列帧动作"的生成路线（首发方案待 1–2 天实测后锁定）。
- **业务建模**：建立以"角色"为中心的素材组织逻辑（角色下辖外观设定，动作序列与音频线均挂载于动画之下）。
- **主攻环境**：导出资产完全针对 Cocos Creator 与小游戏远程加载标准进行原生适配。

**明确延后与不做**：

- **降级支持**：Godot、Unity 等主流引擎适配降为后续工作，前期暂不投入精力。
- **明确不做**：不做骨骼动画（不输出 Spine 数据）；不做 UI、环境道具、场景、tileset、宣传图及 3D 等非角色类资产。

## 三、基本概念

### 3.1 项目

项目是组织角色的顶层单位，对应一款游戏或一次 Game Jam。

- 记录题材、美术风格、目标环境（如"手绘横版 / Cocos Creator / 微信小游戏"）。
- 项目级风格约束作用于旗下所有角色：同一项目内新角色默认继承项目风格，保证多角色风格统一。
- 目标环境决定导出包的形态（见 3.6）。

边界：项目内的角色与资产管理（角色卡、造型、动作清单、版本等）是核心能力；同一角色或资产的跨项目复用为后续（见 3.2 边界）。

### 3.1.1 资产模型总览
> 核心思路：角色是"一个人"（身份稳定），外观由可穿戴组件拼装；服装、服饰、动作都是能独立复用的资产。

信息结构：

```
项目
├─ 角色（身份：脸、体型、关键标志、参考图）
│   └─ 造型（角色 + 一套穿戴组件 → 一张基准帧）
│        └─ 动作实例（该造型下某动作的成套帧）→ 帧
├─ 穿戴资产库：服装 / 服饰 / 装备（可跨角色、跨项目复用）
└─ 动作库：动作定义（规格模板，可复用）
```

### 3.2 角色与角色卡（角色的静态内容）

角色是生成的基本对象，代表"一个人"而非一张图。它的静态内容（外观）分角色身份与造型两层，角色卡是这套静态内容的事实来源,一切动作生成都受它约束。

构成：

- **结构化描述**：名称、配色、服装、装备、比例、关键特征（如"断刃、红围巾"）
- **基准帧**：一张定妆图，是该角色的标准形象，后续所有帧与它比对
- **参考图**：用户上传的原图（可无）

系统从这三者中提取出三类可复用资产：

- **角色身份**：跨造型稳定的部分——名字、脸、年龄、体型、关键标志（如断刃、独眼）、参考图。角色身份与造型无关，角色身份确定后可以更换造型而角色特征保持基本不变。
- **造型**：角色穿上一套具体服装/服饰后的样子 =「角色身份 + 一组穿戴组件」，每个造型有自己的基准帧（这套打扮的定妆图）。同一角色可有多个造型（常态 / 金甲 / 受伤态），换装 = 切换或新建造型。
- **穿戴资产（服装 / 服饰 / 装备）**：组成造型的可复用组件，每件独立成卡。

角色卡 = 角色身份卡（跨造型不变）+ 当前造型的基准帧与外观。生成任何一帧的约束 =「角色身份 + 当前造型基准帧」。

行为：

- 建角色 = 输入描述或上传参考图 → 产出身份 + 首个造型的基准帧候选 → 用户确认 → 角色卡锁定。
- 加造型 / 换装 = 在角色下新建造型，选用已有穿戴资产或新建 → 产出该造型基准帧。
- 锁定后角色卡只读；改形象生成新版（旧版保留，已生成动作不受影响）。
- 每帧生成携带「角色身份 + 造型基准帧」为约束，自动质检据此逐项比对。

这样做的考虑：

- **资产可提取、迁移、复用是贯穿全模型的原则**：角色身份、造型、穿戴资产乃至动作，都能从一个角色里提取出来、迁移到另一个角色或项目、被复用——同一件穿戴资产创建一次，即可供多个角色使用。将角色从单张定妆图拆分为身份与可复用组件，正是为使这一点成立。
- 身份与造型分层，才能表达同一角色的多套造型（换装、形态）——真实游戏角色的常态；否则每套造型只能当成互不相干的新角色。
- 分层 + 版本化让"同一角色"在工程上可定义：凡引用同一身份的造型与帧，属于同一角色。

边界：

- 角色卡只服务于视觉约束；人设背景、世界观等叙事暂缓。
- MS1 只做单角色 · 单造型；多造型 / 换装 / 穿戴资产库 / 跨项目复用为自然延伸，排在核心闭环之后（模型留接口）。

### 3.3 动作（角色的动态内容）

动作是角色的动态内容——它怎么动，如 idle、walk、attack。动作分可复用的定义与随造型渲染的实例两层。

构成：

- **动作定义**：可复用模板——名称、文字描述、姿势参考（可选）、规格（方向、是否循环、FPS、目标帧数、画布尺寸、脚底线、锚点）。定义一次可套到任意造型。清单不预设固定菜单：标准动作直接选，自定义动作（如"拔刀居合"）由用户文字描述创建。
- **动作实例**：某造型下该动作的成套帧。像素随造型不同——金甲的 walk 与布衣的 walk 是两个实例，共用同一份 walk 定义。

行为：

- 用户在角色 / 造型下添加动作，形成动作清单；每个动作实例独立生成、独立检查、独立通过。
- 规格挂在动作定义级：同一实例的所有帧共享同一套画布、脚底线、锚点；帧只记录相对规格的实测偏差。
- 动作定义可提取、迁移、复用：一份 walk 跨造型、跨角色套用，各渲染各的实例。
- 标准动作按内置模板生成；自定义动作按描述生成，经同一套质检。

这样做的考虑：

- 定义与实例分层，动作才成为可复用资产：动作是"怎么动"的抽象，与"谁在动、穿什么"解耦；换造型 / 角色套用同一定义即可，不必重描述。
- 规格放动作定义级而非帧级，"统一画布、脚底线对齐"才有约束源；防抖质检在动作级规格上才可判定。
- 清单可定制而非固定菜单，因为每个游戏需要的动作不同；idle / walk / attack 是本期验收基线，不是上限。

边界：

- 本期动作为单方向（横版，反向靠镜像）；多方向是规格取值扩展，不改概念结构。
- MS1 只在单造型上跑通 idle / walk；动作跨造型 / 跨角色复用为自然延伸。

### 3.4 帧

帧是生成与检查的最小单位，一个动作由按序排列的若干帧构成。

字段：序号、图片、所属动作、所属生成批次、状态、实测偏差。

状态机：待审核 → 通过 / 退回。退回的帧单独重生成，不影响已通过的帧。

行为：

- 自动质检先行：每帧生成后自动比对角色卡（一致性）与动作规格（对齐、偏差），不合格自动标退回。
- 用户逐帧检查：预览播放可暂停、逐帧查看，可手动退回任何一帧。
- 单帧重生成携带相邻帧作为上下文，保证前后接续。

这样做的考虑：竞品"16 帧坏 1 帧只能整套重抽，失败照样扣额度"是实名痛点；帧级状态机把失败局部化，返工成本从一套降到一帧。

边界：帧不可手绘编辑（本期无画笔工具）；修帧的唯一手段是重生成。

### 3.5 生成批次

批次是一次生成调用的完整记录，是可追溯与可复现的载体。

字段：提示词、参考条件（角色卡版本、姿势参考）、技术路线、模型与工具、耗时、成本、产出帧列表。

行为：

- 每帧永远可溯源到产生它的批次；单帧重生成即产生新批次。
- 批次记录对用户可见：一个角色用了多少次生成、多少成本、哪条路线，一目了然。

这样做的考虑：

- 生成路线可替换是关键决策：产品对外承诺的是帧层面的输出契约（尺寸、对齐、一致性），不绑定单一模型；路线信息收在批次里，换路线不动概念结构。
- 完整记录是开源可复现差异化的基础：任何人可按批次记录重放整条链路。

边界：本期不做配额与预算管理。

### 3.6 导出包

导出包是最终交付物：一个角色若干已通过动作的完整快照，下载后可直接进入游戏项目。

内容：GIF 预览、逐帧透明 PNG、sprite sheet（图集）、JSON metadata（帧序、FPS、锚点、脚底线）、目标引擎导入说明、授权与生成记录说明。

行为：

- 只有全部帧通过的动作才进入导出包；有帧未通过则该动作不可导出，不产出残缺包。
- 按项目的目标环境出包：首期为 Cocos Creator / 微信小游戏（图集与命名符合其导入习惯，目录按远程加载组织——角色资源默认不进 4MB 主包）；Web 通用预览始终可用。

这样做的考虑（为什么交付序列帧、不含骨骼数据）：

- **用户匹配**：序列帧是所有引擎原生支持的最低公分母，零运行时依赖；骨骼资产要求绑定、蒙皮、运行时知识，目标用户出问题修不了。
- **可行性**：骨骼自动生成需要模型从图片反推结构化数据（拆件、锚点、骨架拓扑），是当前模型的已知弱项，有一手失败记录（知乎 spine 生成失败实录，链接见痛点证据文档）；8 周内攻坚不现实。
- **覆盖面**：像素风、载具、非人形，骨骼做不了，序列帧全覆盖。
- **可验证**：序列帧质量判据（漂移像素、对齐、导入可播）全部可写成自动化测试；骨骼质量（拆件合理性、权重自然度）无客观判据。
- **包体顾虑的回应**：4MB 限的是主包，行业标准解法是远程加载（咸鱼之王拆包实证）；序列帧图集同样可分包、可远程加载。

边界：不输出 Spine/DragonBones 数据；导出包不含引擎插件，导入说明基于引擎原生资源。

## 四、核心流程与原型（待继续讨论完善）

用户视角端到端（标注：AI 生成 / 人确认 / 工程自动）：

1. 创建项目，设定题材、风格、目标环境（人）
2. 输入角色描述或上传参考图（人） → 产出角色卡候选（AI） → 修改并锁定（人）
3. 添加动作：标准清单直选，或文字描述自定义，确认规格（人）
4. 逐动作生成（AI） → 自动质检（一致性 + 对齐）（工程）
5. 动画预览与逐帧检查（人），退回的帧单独重生成（AI）
6. 全部通过后导出素材包（工程），放入 Cocos Creator 首次播放

MS1 原型按此流程串联，允许占位素材与模拟生成结果，重点验证用户是否理解角色卡、动作清单、逐帧检查与导出；真实生成效果由后续里程碑验证。原型图待本文文字定稿后补（01 规范两步法）。

## 五、核心假设与验收

### 5.1 MVP 核心假设

| # | 核心假设（命题） | 验证方式 | 通过标准 | 失败退路 |
|---|---|---|---|---|
| 1 | 目标用户要的是"能进项目的动作资产"，不是更多单张角色图 | 5–8 名目标用户对比单图与可预览、可导出的动作工作流，完成一次原型任务 | ≥4 人独立完成，并认可动作补齐或工程导出的价值 | 收缩为角色基准管理与动作素材整理工具 |
| 2 | 角色卡（基准帧 + 结构化描述 + 参考图）能把跨动作一致性提到可用水平 | 普通提示词与本方案各生成三动作，按脸、服装、配色、体型盲评 | ≥80% 动作帧被多数评审判为同一角色，且优于提示词基线 | 收窄角色类型与主风格；增加首帧确认后再补帧 |
| 3 | 单方向 idle / walk（attack 挑战）足以支撑原型与小游戏核心玩法验证 | 用横版动作、平台跳跃、轻量战斗三个原型场景展示并访谈 | ≥4 人指出明确使用场景，接受先保证基线动作稳定 | 优先补 jump；仍过宽则聚焦 walk + attack |
| 4 | 动作级统一规格（画布、脚底线、锚点、帧序、元数据）能显著降低接入成本 | 用户将同一动作包导入 Cocos Creator，记录耗时与手工校正步骤 | 15 分钟内完成首次播放，无需重切帧、批量改名、逐帧调锚点 | 固定 Cocos 版本与项目模板，提供强预设 |
| 5 | 自定义动作（文字描述创建）能生成可用动画 | 选 3 个非标准动作（含持械技能）实测，与标准动作过同一套质检 | ≥2/3 达到与标准动作同档的一致性与可读性 | 分档承诺：标准动作保证质量，自定义动作标注实验档（待拍板 2） |
| 6 | 中文、开源可复现、生成路线可替换构成相对闭源竞品的采用理由 | 向 5 名目标用户展示闭源成品与开源窄工作流，访谈试用与替换意愿 | ≥3 人愿试用或反馈，认可可控性、可替换性或国内链路适配 | 差异化收敛到角色一致性与 Cocos / 小游戏交付 |

### 5.2 验收标准

统一用例：手绘风骷髅剑士。

**现状**（不用本产品）：三个动作逐个用提示词碰运气，进 Cocos 前手工去背、切帧、对齐、改名、配置，耗时以小时计且结果不稳定。

**提议后形态（逐条可判过 / 不过）**：

1. **全流程可跑通**：5–8 名目标用户试用，≥4 人无需讲解完成"角色输入 → 角色卡确认 → 动作选择 → 逐帧检查 → 导出"全流程（假设 1）。
2. **产出物**：单次任务产出同一角色（单造型）的 idle（4–6 帧）与 walk（6–8 帧），可循环完整播放；attack 为挑战项，验证可行性，不作本期硬性通过条件（假设 3）。
3. **角色一致性**：动作帧经盲评被多数评审判为同一角色的比例 ≥80%，且优于纯提示词基线（假设 2）。
4. **对齐与帧间稳定**：画布一致、背景透明，脚底线对齐无肉眼可见跳动（量化阈值初设帧高 3% 以内，第 1–2 周实验校准，见待拍板 3）。
5. **单帧重生成一致性**：对任一帧执行单帧重生成后，该帧与相邻帧不出现可见抖动或角色漂移（本期路线的关键风险，纳入实验专项验证）。
6. **引擎适配**：导出包在 Cocos Creator / 微信小游戏首次播放成功，无需重切帧、批量改名、逐帧调锚点（假设 4）。本期只验收国产靶子；Godot、Unity 不在本期验收范围。
7. **工作流成功率**：由自动评估流程统计，单次生成产出可用帧的成功率 ≥70%（"可用"以一致性与对齐质检为判据）。
8. **成本与速度**：记录并报告每角色的生成次数、耗时、成本（MS1 三个数），作为路线选型与后续优化的基线。
9. **过程可追溯**：每帧可溯源到生成批次（提示词、参考、路线、次数、耗时、成本）；相关文档完整、代码可追溯。

**边界与非法情况**：

10. 缺角色卡、动作帧不全或规格检查失败时明确报错，不导出残缺包。
11. 验收不含：多方向、换装、骨骼、特效、UI / 道具 / 场景、3D、GDD、完整引擎插件。
