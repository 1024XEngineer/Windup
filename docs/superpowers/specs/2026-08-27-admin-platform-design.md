# Windup 独立管理平台与运行时配置中心设计

日期：2026-08-27

状态：设计已确认，等待实施计划评审

目标域名：`admin.windup.xin`

## 1. 决策摘要

Windup 新增独立管理平台，沿用仓库现有的 React、TypeScript、Vite、FastAPI、SQLAlchemy、PostgreSQL 与 Redis 技术栈。SmartAdmin 仅作为后台产品结构与交互参考，不引入其 Vue、Java 或 Spring Boot 代码。

管理平台与普通用户站点彻底隔离：独立域名、独立管理员账号、独立认证令牌、独立 `/admin-api/*` 接口及独立权限模型。普通 Windup 用户即使已登录，也不能访问管理接口；管理员账号也不自动获得普通用户身份。

本项目采用**迁移优先**原则，不重新实现 Windup 已有业务能力。兑换码、敏感词、用户、积分和 AI Gateway 继续使用当前领域模型、服务、数据与 Provider Adapter；管理平台只接管它们的管理入口、权限、配置来源和发布流程。只有现有系统确实缺失的独立管理员认证、RBAC、审计、配置版本与发布机制才新增实现。

管理平台负责以下资源：

- AI Provider、访问凭据和服务地址；
- 图像模型、视频模型及能力参数；
- 模型路由、入口切换、降级与熔断策略；
- 敏感词词库；
- 积分兑换码；
- 用户与用户状态；
- 用户积分账户、积分流水和人工调整；
- 管理员、角色、权限、配置版本与审计日志。

业务运行配置从 `.env` 迁移到具名、强类型的数据库表。环境变量只保留数据库、Redis、管理令牌签名密钥、配置加密主密钥等启动所必需的引导配置。

## 2. 目标与非目标

### 2.1 目标

1. 管理员可在网页中安全地维护所有受管资源，不再通过编辑服务器 `.env` 完成日常业务配置。
2. 配置修改必须经过草稿、校验、发布、回滚流程，不能保存后立即影响生产流量。
3. Backend 与 Worker 使用同一份不可变配置快照，并能在不重启容器的情况下加载新版本。
4. 每次高风险操作均记录操作者、对象、前后值摘要、时间和请求来源。
5. 积分和兑换码保持账务可追溯，禁止直接改余额或恢复已暴露的兑换码明文。
6. 管理平台可逐模块交付，不要求一次性替换全部现有机制。

### 2.2 非目标

- 不引入 SmartAdmin 的 Vue、Java、Spring Boot 或数据库模型。
- 不与普通用户共用账号、会话、JWT 或登录页。
- 不允许管理平台编辑数据库地址、Redis 地址、令牌签名密钥或配置加密主密钥。
- 不向前端返回 API Key 明文，不提供“查看原密钥”功能。
- 不允许直接修改历史积分流水或历史发布版本。
- 不在未校验的情况下把草稿配置应用到生产流量。
- 本设计阶段不修改生产 DNS、Nginx、容器或服务器配置。

## 3. 当前 main 现状

当前 `main` 已有以下基础能力：

- `admin_quota.py` 提供兑换码生成与校验接口，但管理员身份仍是普通用户会话加邮箱白名单，不符合独立管理员账号要求。
- 兑换码数据库只保存摘要，明文仅在生成响应中返回一次；该安全约束继续保留。
- 敏感词已使用 `windup_sensitive_word` 表作为唯一真相，并有 Redis 缓存与跨进程刷新能力；缺少独立管理接口、权限和操作审计。
- `AIProviderSettings` 仍从环境变量读取 Provider、模型、URL、密钥、fallback 等配置。
- Gateway 的部分重试、路由与熔断参数仍由代码或进程内对象固定，例如熔断冷却时间默认 60 秒。
- 普通用户认证、积分账户和生成任务链路已经存在，应复用领域能力，但不能复用为管理员认证。

因此，本项目不是另起一套 AI 调用系统，而是在现有网关和业务服务上增加独立控制面，并把运行时配置改为版本化快照。

### 3.1 搬迁原则

现有能力搬迁遵守以下规则：

1. **领域服务不复制**：兑换码继续调用 `windup_app.server.quota.redemption`，敏感词继续调用 `windup_app.server.sensitive_word`，用户与积分继续复用现有 user/quota 服务，模型请求继续进入 `windup_framework.gateway` 及已有 Provider Adapter。
2. **数据真相不复制**：现有业务表继续作为唯一真相；只在确有新概念时增加关联表或字段，例如兑换批次、管理员、权限、审计和配置版本。
3. **管理入口搬迁**：先为现有服务增加独立 `/admin-api/*` 适配层和 RBAC，再让新 Admin SPA 使用这些接口；验收通过后下线旧邮箱白名单入口。
4. **配置来源搬迁**：把当前 `AIProviderSettings` 可管理字段导入配置草稿，经发布后由运行时快照提供；Gateway 的协议、请求形状和实际调用实现保持不变。
5. **逐模块切换**：每个模块先盘点现有能力与缺口，再实现最小适配，完成数据兼容和回归测试后切换入口，禁止在切换期间形成两套可写真相。
6. **缺口才新增**：如果现有服务不能满足管理需求，应优先扩展原服务；只有职责明确独立且当前不存在的能力才建立新模块。

## 4. 总体边界

```text
admin.windup.xin
  └─ React Admin SPA
       └─ /admin-api/*
            ├─ 独立管理员认证与 RBAC
            ├─ 配置草稿/发布/回滚
            ├─ 用户、积分、兑换码、敏感词
            └─ 审计与版本记录

PostgreSQL
  ├─ 管理员与权限表
  ├─ 运行时配置表/不可变快照
  └─ 既有业务表

Redis
  ├─ 管理员会话撤销与限流
  └─ config:published 通知

Backend / Worker
  └─ 读取同一已发布快照，失败时保留 last-known-good
```

管理平台作为同一仓库中的独立应用入口构建和部署，但不嵌入普通用户应用路由。后端仍是同一个 FastAPI 服务进程，管理接口以独立路由树、认证依赖和审计中间件隔离。

## 5. 独立管理员认证与权限

### 5.1 身份模型

新增独立表：

| 表 | 用途 |
|---|---|
| `windup_admin_user` | 管理员邮箱、密码摘要、状态、最后登录时间、强制改密标记 |
| `windup_admin_role` | 角色定义 |
| `windup_admin_permission` | 原子权限定义 |
| `windup_admin_user_role` | 管理员与角色关系 |
| `windup_admin_role_permission` | 角色与权限关系 |
| `windup_admin_refresh_token` | 仅管理员域使用的可撤销刷新令牌 |
| `windup_admin_audit_log` | 管理操作审计 |

管理员不开放注册。首个超级管理员通过一次性 CLI 在服务器创建；后续管理员由具备 `admin.manage` 权限的人创建、停用、重置密码和分配角色。

V1 使用独立邮箱和密码登录，访问令牌短时有效，刷新令牌轮换并保存摘要。停用管理员、重置密码、撤销会话后，已有刷新令牌立即失效。管理员 Cookie 使用 `Secure`、`HttpOnly`、`SameSite=Strict`，并限制到管理域和管理接口路径。

### 5.2 权限粒度

最低权限集合：

- `gateway.read`、`gateway.write`、`gateway.publish`、`gateway.rollback`
- `credential.read`、`credential.rotate`、`credential.test`
- `model.image.manage`、`model.video.manage`
- `routing.manage`、`circuit.manage`
- `sensitive_word.read`、`sensitive_word.write`
- `redemption.read`、`redemption.create`、`redemption.disable`、`redemption.export`
- `user.read`、`user.manage`
- `credit.read`、`credit.adjust`
- `admin.manage`、`role.manage`、`audit.read`

后端按接口执行权限校验，前端权限仅用于隐藏或禁用控件，不能作为安全边界。高风险操作需要二次确认并填写原因；发布、回滚、密钥轮换、积分调整和管理员变更全部强制审计。

## 6. 配置领域模型

禁止使用一个通用 JSON/KV 表承载全部配置。每类资源必须有明确字段、约束与外键：

| 表 | 关键内容 |
|---|---|
| `windup_ai_provider` | Provider 名称、协议适配器、启用状态、超时等 |
| `windup_ai_provider_credential` | 加密密钥、密钥版本、状态、掩码尾号 |
| `windup_ai_endpoint` | Provider 下的 Base URL、优先级、健康状态与用途 |
| `windup_ai_model` | 图像/视频/聊天模型、能力、成本、版本与启用状态 |
| `windup_ai_route_policy` | 按能力或场景选择的路由策略 |
| `windup_ai_route_step` | 有序候选模型、端点、凭据池及匹配条件 |
| `windup_ai_fallback_policy` | 可降级错误、最大跳数和降级链 |
| `windup_ai_circuit_policy` | 失败阈值、统计窗口、冷却时间、半开探测 |
| `windup_runtime_config_version` | 草稿版本、状态、创建人与来源版本 |
| `windup_runtime_config_snapshot` | 发布时生成的不可变完整快照 |
| `windup_runtime_config_release` | 发布时间、发布人、回滚来源与校验结果 |

模型类型至少区分 `image`、`video`、`chat`、`judge`，同时保留协议适配器字段。请求体形状仍由代码中的 Provider Adapter 决定，管理平台只能在适配器声明的能力和参数范围内配置，避免把协议结构变成任意 JSON 后延迟到付费请求时才失败。

### 6.1 密钥保护

- 配置加密主密钥仅存在于服务器环境变量或密钥管理服务中。
- 数据库存储密文、nonce、算法和密钥版本，不存明文。
- 管理端只显示凭据名称、状态和尾号；创建或轮换后不再返回完整密钥。
- “测试连接”由后端使用密钥执行最小成本探测，响应只给出成功、错误类型和脱敏摘要。
- 日志、审计和 API 错误都必须经过密钥与 URL 查询参数脱敏。

## 7. 草稿、发布与运行时加载

### 7.1 状态流

```text
编辑草稿
  → 结构校验
  → Provider/模型能力校验
  → 可选连通性探测
  → 发布事务生成不可变 snapshot
  → Redis 广播 version_id
  → Backend/Worker 拉取并原子替换
```

草稿可以反复保存，但不会改变生产行为。只有具备 `gateway.publish` 的管理员可发布。发布前至少校验：外键完整、路由无环、每条启用路由有可用端点和凭据、模型能力匹配、fallback 跳数有限、熔断参数范围合法。

### 7.2 一致性规则

1. 发布事务一次性写入快照与发布记录，并更新唯一的当前发布版本指针。
2. Backend 与 Worker 收到 Redis 通知后按版本号加载完整快照，校验成功后原子替换内存引用。
3. 加载失败时继续使用 last-known-good，并记录告警；不得部分应用新配置。
4. Redis 不可用时，进程继续使用 last-known-good，并通过低频数据库版本检查恢复同步。
5. 回滚不是修改旧版本，而是把指定历史快照重新发布为新版本。
6. 网关、trace、ledger 与 Provider 调用都显式接收同一个运行时快照，禁止通过修改模块级单例实现临时开关。

### 7.3 任务版本绑定

新生成任务在创建时记录 `runtime_config_version_id`。Worker 执行或恢复任务时加载该版本，保证排队、重试和恢复期间不会因后台发布而换模型或换计费策略。已经开始执行的任务不切换版本；只有新任务使用最新发布配置。

## 8. 管理功能模块

### 8.1 概览

展示当前发布版本、待发布草稿、Provider 健康摘要、熔断状态、近期开销、任务失败率、兑换码与积分异常。概览只聚合数据，不提供绕过权限的快捷写操作。

### 8.2 Provider、凭据与 URL

- 新增、编辑、启停 Provider。
- 维护多个服务地址及优先级，标记主入口与备用入口。
- 新建、轮换、停用凭据，执行脱敏连通性测试。
- 查看最近健康状态和失败摘要。
- 禁止删除已被发布版本引用的资源；使用停用代替硬删除。

### 8.3 图像模型与视频模型

图像和视频模型使用同一领域模型，但页面分开，避免能力参数混杂。字段包括 Provider、远端模型名、能力、允许尺寸/时长、成本、协议适配器、启用状态和可用范围。用户白名单或灰度范围使用结构化规则，不再使用逗号分隔的环境变量。

### 8.4 路由、降级、熔断与 URL 切换

- 为 `image`、`video`、`chat`、`judge` 等能力维护有序路由链。
- 明确哪些错误可换 Key、换 URL、换模型或直接失败。
- 配置失败阈值、窗口、冷却时间和半开探测次数。
- 提供“用模拟输入做纯校验”和“经确认执行真实探测”两种测试；真实探测必须标记可能产生费用。
- 页面展示最终解析出的链路，避免管理员只看到分散配置而无法判断真实执行顺序。

### 8.5 敏感词

复用现有 `windup_sensitive_word` 表和热更新服务，新增独立管理 API 与页面。支持分页查询、分类筛选、批量导入、新增、编辑和启停。删除操作表现为停用，不物理删除历史记录。每次变更发布刷新事件，并记录命中规则以外的管理审计，不在审计中记录用户敏感原文。

### 8.6 兑换码

保留“数据库只存摘要、明文只返回一次”的既有约束，并新增批次模型：

- 按批次生成、设置积分额度、有效期和备注；
- 生成完成后只提供一次明文复制/下载；
- 可按批次、摘要尾号、状态、兑换人和时间筛选；
- 可停用未兑换代码或整个批次；
- 查看兑换记录和审计记录；
- 已兑换代码不可恢复、不可再次导出明文。

建议新增 `windup_credit_redemption_batch`，既有兑换码表关联 `batch_id` 并增加停用状态与操作者信息，历史数据通过兼容批次归档，不改变已兑换事实。

### 8.7 用户与积分

用户列表支持按 ID、邮箱、状态和创建时间查询；详情页展示基本信息、账号状态、积分余额、最近任务、兑换记录和积分流水。用户停用、恢复等操作需要 `user.manage`。

积分余额不能直接覆写。人工增减积分必须创建不可变流水，包含管理员、原因、关联对象、幂等键、调整前后余额和时间。相同幂等键不得重复入账。撤销一次错误调整时创建反向流水，不修改原流水。

### 8.8 管理员、角色与审计

超级管理员可创建/停用管理员、重置密码、分配角色和撤销会话。角色权限变更必须记录变更前后权限集合。

审计页支持按管理员、资源类型、动作、结果、时间和请求 ID 查询。密钥明文、密码、令牌、兑换码明文和用户输入原文永不进入审计详情。

建议路由：

```text

/admin-api/credentials/*

/admin-api/models/*
/admin-api/routes/*
/admin-api/fallback-policies/*
/admin-api/circuit-policies/*
/admin-api/config-versions/*
/admin-api/sensitive-words/*
/admin-api/redemption-batches/*
/admin-api/redemption-codes/*
/admin-api/users/*
/admin-api/credit-transactions/*

```

所有列表接口统一提供游标或稳定排序分页、明确筛选字段和最大页大小。所有写接口使用 Pydantic 严格模型并拒绝额外字段。发布、回滚、积分调整和批量停用支持幂等键。

## 10. 前端结构

继续使用现有 `frontend` 包，但增加独立 Admin 构建入口，不把后台路由挂进普通站点：

```text
frontend/src/admin/
  app/
  pages/
  entities/
  features/
  shared/
```

Vite 生成独立管理入口和静态产物。Admin SPA 使用独立 `AdminShell`、登录页、权限守卫、错误边界、表格与表单组件；共享现有基础设计令牌和通用无业务组件。管理平台视觉保持 Windup 品牌，但信息密度、筛选与批量操作按后台工作场景设计。

前端不得保存 API Key、管理员密码或兑换码明文到 localStorage。权限变更或 401/403 时立即清除管理会话状态并回到管理员登录页。

## 11. 部署与域名

生产部署时新增：

1. `admin.windup.xin` DNS 记录；
2. 独立 TLS 证书或覆盖该域名的证书；
3. Nginx 独立 server block，管理静态产物只在该域名提供；
4. `/admin-api/` 反向代理到现有 Backend；
5. 管理域设置严格 CSP、`X-Robots-Tag: noindex, nofollow` 和独立访问日志；
6. 登录、验证码、密钥测试、发布和积分调整接口设置更严格限流。

第一阶段 PR 只提交代码、迁移与部署模板，不直接修改生产 DNS 或服务器。

## 12. 迁移方案

1. 增加管理员、RBAC、审计、配置中心和兑换批次表。
2. 逐项建立“现有模块 → 管理入口 → 数据表 → 运行时消费者”搬迁清单，确认复用点和真实缺口后再编码。
3. 提供一次性导入命令，把当前 AI 环境变量解析为首个配置草稿；导入时不打印密钥。
4. 管理员校验并发布首个快照后，Backend 与 Worker 优先读取数据库发布版本。
5. 过渡期保留 AI 环境变量只读 fallback；确认所有实例稳定读取发布版本后，移除业务 AI 环境变量 fallback。
6. 敏感词数据和服务继续使用现有实现，只搬迁管理入口与权限，不建立第二套词库。
7. 既有兑换码和积分流水保持原记录，通过兼容迁移补充批次或审计关联，不重算余额，不复制业务服务。
8. 旧 `/admin/quota/redemption-codes` 在新管理接口验收后下线，不能长期保留邮箱白名单旁路。

## 13. 失败处理与安全原则

- 管理认证或权限状态不明确时拒绝访问，不降级为普通用户认证。
- 配置校验或加载失败时拒绝发布，运行时继续使用 last-known-good。
- 发布后部分实例未确认加载时显示“部分生效”告警，并允许安全回滚。
- 数据库或 Redis 短时故障时，正在运行的生成任务继续使用已绑定快照。
- 配置、积分和兑换码写操作使用数据库事务；跨存储操作使用可重试的发布/通知记录，不伪装成原子事务。
- 所有管理请求带 request ID；审计失败不能静默吞掉，高风险写操作在审计记录无法落库时失败关闭。

## 14. 测试与验收

### 14.1 后端

- 普通用户令牌访问任意 `/admin-api/*` 均返回 401/403。
- 管理员登录、刷新轮换、停用、改密和会话撤销测试。
- RBAC 每个权限的允许与拒绝路径测试。
- 凭据加密、脱敏、轮换与日志不泄密测试。
- 配置草稿校验、发布、热加载、部分失败、回滚和 last-known-good 测试。
- 新任务绑定版本、排队任务恢复仍使用原版本测试。
- Provider/模型能力不匹配、路由成环、无可用凭据等发布拒绝测试。
- 敏感词增改停用及跨进程刷新测试。
- 兑换码一次明文、批次停用、已兑换不可恢复测试。
- 积分调整幂等、并发余额、反向流水和审计测试。
- 数据库迁移升级与回滚边界测试。

### 14.2 前端

- 管理登录、401/403、权限控件、路由守卫和会话失效测试。
- Provider、模型、策略、敏感词、兑换码、用户和积分表单校验测试。
- 草稿差异、发布确认、回滚确认和密钥不可回显测试。
- 列表分页、筛选、空态、失败重试和审计详情测试。
- 独立 Admin 构建不包含普通用户路由，普通站点构建不暴露 Admin 页面测试。

### 14.3 端到端验收

1. 创建独立管理员并登录。
2. 导入现有 AI 配置为草稿，完成校验和发布。
3. Backend 与 Worker 同时加载同一版本，新任务记录版本号并正常生成。
4. 发布错误配置被拦截；发布有效备用配置后可切换，再可回滚。
5. 管理敏感词并验证无需重启即可生效。
6. 生成兑换码、一次导出、用户兑换、后台追踪和批次停用完整通过。
7. 查看用户积分流水并执行一笔有原因、有幂等键、可审计的人工调整。
8. 普通用户账号无法登录或访问管理平台接口。

## 15. 分阶段 PR

为避免超大 PR，按依赖顺序拆分：

1. **管理基础**：独立 Admin 构建入口、管理员认证、RBAC、审计骨架。
2. **配置内核**：配置表、加密凭据、草稿/发布/回滚、运行时快照加载与任务版本绑定。
3. **AI 管理界面**：Provider、URL、图像/视频模型、路由、降级、熔断的 API 与页面。
4. **内容与兑换**：敏感词管理、兑换批次、兑换码列表/停用/导出及旧接口收口。
5. **用户与积分**：用户查询/状态管理、积分流水和人工调整。
6. **部署与验收**：`admin.windup.xin` 部署模板、数据导入、全链路测试和生产上线清单。

每个 PR 必须独立关联对应 Issue，只包含本阶段需要的迁移、代码、测试和文档。前一阶段合并并同步最新 `main` 后再开始下一阶段。

## 16. 完成标准

管理平台完成不以“页面可打开”为标准，而以以下条件全部满足为准：

- 管理员身份与普通用户身份完全隔离；
- 既有兑换码、敏感词、用户、积分和 Gateway 能力均由原领域服务承载，不存在并行的第二套实现或第二份可写数据真相；
- 所有受管资源均有后端权限校验和审计；
- 日常 AI 业务配置不再依赖服务器手改 `.env`；
- Backend 与 Worker 使用同一不可变发布快照，任务可稳定恢复；
- 密钥、兑换码和积分均符合不可回显、不可篡改、可追溯约束；
- 管理页面覆盖 Provider、模型、策略、敏感词、兑换码、用户、积分、管理员和审计；
- 自动化测试与生产验收清单通过；
- `admin.windup.xin` 独立部署并拒绝普通用户会话。
